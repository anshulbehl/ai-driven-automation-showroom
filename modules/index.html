Hands-On AIOps: Building Self-Healing, Observability-Driven Automation with Ansible

1. Background

AIOps stands for artificial intelligence for IT operations. It refers both to a modern approach to managing IT operations and to the software systems that implement it. AIOps uses data science, big data, and machine learning to augment, or even automate, many of the processes traditionally handled manually by IT teams. Its goal is to improve issue detection, root cause analysis, and system resolution by making IT operations more intelligent and efficient. To read more about AIops there is a great article on redhat.com.

In AIOps there are three major parts:

  • Observability

  • Inference

  • Automation

  • Observability is the ability to understand the internal state of a system by collecting, analyzing, and visualizing data from logs, metrics, and traces. This can be another AI tool such as IBM Instana Observability. For this lab we are simply relaying logs using Filebeat, a Lightweight shipper for logs. Ansible Automation Platform can integrate with observability tools using Event-Driven Ansible (EDA).

  • Inference - Inference in AI refers to the process of using a trained model to make predictions or decisions based on new, unseen data. For this AIOps workflow we are using Red Hat AI for understanding service issues like an application outage, and Automation coding assistant to create an Ansible Playbook.

  • Automation is the ability to automatically detect, respond to, and resolve IT issues without human intervention. We are using Ansible Automation Platform to tie observability and inference together directly to create workflows for self-healing infrastructure.

It is important to note that AIOps can be adopted incrementally and it is not all or nothing. You do not need to have fully self-healing infrastructure on day one to start realizing value. At Red Hat we like to say: "Start small, think big!"

2. Lab Environment

2.1. Core Observability

  • IBM Instana - Enterprise observability platform monitoring applications and infrastructure

    • Intelligent anomaly detection with Smart Alerts

    • Distributed tracing and service dependencies

    • Action Catalog integration with AAP for NLP-based remediation recommendations

    • Webhook integration with Event-Driven Ansible for automated response

  • Filebeat - Lightweight log shipper monitoring Apache logs

  • Kafka - Distributed event streaming platform for real-time event transport

2.2. Automation & Orchestration

  • Ansible Automation Platform (AAP) - Enterprise orchestration and automation

    • Automation Controller for job template and workflow execution

    • Event-Driven Ansible (EDA) for event-based automation triggers

    • Integrated with Instana for bidirectional event flow

  • Event-Driven Ansible (EDA) - Listening to Kafka, webhooks, and Instana alerts to launch workflows

  • Gitea for source control management of Ansible Playbooks

  • Mattermost for automated notifications during workflows

2.3. AI & Inference

  • Red Hat AI - LLM inference service for incident analysis and context enrichment

  • Automation coding assistant (formerly Ansible Lightspeed) - AI-powered playbook generation

  • Red Hat Lightspeed (console.redhat.com) - CVE and Advisor remediation recommendations

  • code-server (VS Code in the browser) with Claude Code as the AI agent

  • Claude Code Ansible MCP Server - AI agent integration with AAP through Model Context Protocol

  • CrewAI agent framework for autonomous AI-driven incident response

2.4. Monitored Systems

  • Three RHEL (Red Hat Enterprise Linux) nodes

    • node1: Apache webserver (httpd)

    • node2: Flask web application (lab-webapp) with the Instana agent for APM

    • node3: Additional node for system role configuration

  • A Windows Server with Active Directory for Windows event-driven automation

  • Winlogbeat on Windows forwarding events to Kafka

EDA (Event-Driven Ansible) is part of Ansible Automation Platform. It is referred to separately sometimes depending on the workflow. EDA uses rulebooks to monitor events, then executes specified job templates or workflows based on the event. Think of it simply as inputs and outputs. EDA is an automatic way for inputs into Ansible Automation Platform, where Automation controller / Automation execution is the output (running a job template or workflow).

4. EDA Rulebook Activation Management

Read this before starting any section.

This lab uses four Event-Driven Ansible (EDA) rulebook activations. Three are running when your lab starts, and one is intentionally left disabled because it would conflict with another. Here is the starting state:

There is only one conflict to manage. Web App and AI Agent consume the same Kafka topic, so running both at once produces duplicate responses to a single Apache failure. AI Agent therefore starts disabled, and Section 5 walks you through swapping them over and swapping back afterwards.

Everything else runs concurrently. Instana AIOps is the only activation using port 5000, and Windows Events has its own event source. Section 4 (Red Hat Lightspeed and Agentic IDE Workflow) does not use EDA at all.

Section 1 temporarily disables Instana AIOps for one exercise, to show what changes when automated remediation is not armed. That section tells you when to disable it and when to turn it back on. Leave it Running at all other times.

5. Workshop Sections

This workshop consists of five independent sections that can be completed in any order. Together they cover the full AIOps maturity spectrum, from intelligent observability through to autonomous incident response with AI agents.

Section Title Description

Section 1

IBM Instana Observability and Intelligent Remediation

Learn how intelligent observability detects incidents and surfaces recommended remediation. Explore distributed tracing, build an Application Perspective and Smart Alert, then run both paths to remediation: automated through EDA, and operator-driven from the NLP-ranked Instana Action Catalog. (45-60 min)

Section 2

AIOps with Apache Remediation

Build a self-healing workflow for Apache service failures using Red Hat AI and Automation coding assistant. Combine log enrichment, AI-driven prompt generation, and automated remediation. (30-40 min)

Section 3

AIOps with Windows Automation

Extend the AIOps pattern to Windows Server. Detect Active Directory and Windows Firewall events with Winlogbeat and Kafka, then use Event-Driven Ansible to create AI-enriched tickets automatically. (15-20 min)

Section 4

Red Hat Lightspeed and Agentic IDE Workflow

Use Red Hat Lightspeed to generate CVE and Advisor remediation playbooks, use Automation coding assistant to generate an HTTPD fix in code-server, then use Claude Code to interactively discover and remediate issues via the Ansible MCP server. (50-70 min)

Section 5

AI-Driven Incident Response with MCP

Use AI agents that interact with Ansible Automation Platform through the Model Context Protocol (MCP). Progress from human-in-the-loop with Claude Code, to autonomous CrewAI agents, to fully operationalized AI-driven incident response with EDA. (30-40 min)

Total Workshop Time: ~3-4 hours (all sections) or pick individual sections as needed.

5.1. The AIOps Maturity Spectrum

This workshop takes you through the full maturity spectrum:

  • Section 1: Instana detects an outage; EDA runs a predefined restore job, or an operator reviews Action Catalog recommendations

  • Sections 2-3: Event-driven workflows with AI content generation and human review checkpoints

  • Section 4: Human-in-the-loop with an AI agent that asks permission before every action

  • Section 5: AI agents that discover and orchestrate existing automation through MCP, from interactive to fully autonomous

5.2. Workshop Agenda

Section 1 covers Instana observability and the two remediation paths. Section 3 covers Windows events and AI-driven ticketing. Section 2 follows this four-part Apache workflow:

  1. Event-Driven Ansible (EDA) Response - Event Driven Ansible will respond to a systemd application outage

  2. Log Enrichment and Prompt Generation Workflow - Ansible Automation Platform (AAP) will retrieve systemd logs, coordinate with Red Hat AI to analyze the incident, notify Mattermost then automatically create a Job Template for us to use in the subsequent workflow.

  3. Remediation Workflow - This workflow will focus on automatically creating an Ansible Playbook to resolve the issue by using Automation coding assistant. This workflow will take the prompt created by the previous workflow, request a playbook from Automation coding assistant, sync this playbook to Git and then automatically create a Job Template for us to remediate the issue.

  4. Execute a remediation

    Launch Execute HTTPD Remediation to fix the Apache outage on the RHEL webserver after reviewing the generated playbook.

Could this all be one workflow? Yes. This is purposely broken up at natural breakpoints where a human user can review what the AIOps workflow is doing and course correct if required. This also allows organizations to incrementally adopt AIOps workflows. Organizations can benefit greatly from any of these individual sections!

Why Mattermost? Mattermost is an open-source, self-hostable online chat service with file sharing, search, and third party application integrations. It is designed as an internal chat for organisations and companies, and mostly markets itself as an open-source alternative to Slack and Microsoft Teams. It is used in this workshop as an example and can be replaced with any Chat or ITSM (e.g. ServiceNow) of your choice. It is really easy to setup an individual Mattermost container per student in the workshop!
Why Gitea? Gitea is a self-hosted, open-source software development service that provides Git hosting, code review, team collaboration, package registry, and CI/CD, similar to platforms like GitHub, Bitbucket, and GitLab. It could be replaced by Github, Gitlab or any Git service of your choosing. It is a very lightweight solution that works great for workshops.
Why Kafka? Apache Kafka is a distributed streaming platform used for building real-time data pipelines and streaming applications, enabling applications to publish, consume, and process high volumes of data streams. It is all open-source and self hosted and works great for workshops. This could be replaced by any event bus of your choosing. Event-Driven Ansible has numerous plugins including integrations with AWS SQS, AWS CloudTrail, Azure Service Bus, Prometheus, dynatrace, IBM Instana, BigPanda, Zabbix, CyberArk and more.
